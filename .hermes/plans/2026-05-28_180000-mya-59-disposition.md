## Risks, tradeoffs, open questions

**Risk 1:** SDK capability addition is wide-surface — touches 4 SDK files plus host. Mitigation: every other namespace (`issues`, `goals`, `companies`) already follows this exact pattern; this is mechanical pattern-matching, not novel design.

**Risk 2:** `tsx-watch` mid-edit triggers reload races (memory: `process_lost`). Mitigation: use `pnpm dev:once` after the build batch, not `pnpm dev`.

**Risk 3:** Cost replay window is short (24h post-pin). If pre-pin tail dominates, share % will look elevated. Mitigation: report **rolling 6h share** in addition to 24h to surface the trend.

**Open question:** Should the disposition doc include a forward-looking section mentioning MYA-80 ETA? **Recommendation: no.** The verdict's own anti-ceremony rule says deferred is deferred until tension surfaces it. Shipping a roadmap promotes scope creep.

**Open question:** Once MYA-59 is dispositioned, do we delete the `Recover stalled MYA-59`-style auto-spawned siblings from MYA-83/87/88/89/90/91/115/120 etc.? **Recommendation: no.** They're already `done`; deleting rewrites history. The disposition doc explicitly notes them as "scheduler artefacts, not real recovery work."
